## 来源与当前范围

中拆出 TypeScript 项目基础实践标准。

已确认名称方向为 `typescript-project`，作者包名为
`@silvermoon-work/check.typescript-project`。参考
[preset-typescript-base](https://github.com/shazhou-ww/preset-typescript-base)

本轮只编写需求。后续首期实现范围为输入契约、归一化函数、测试及文档，不实现实际项目检测，不生成 Check 制品，不建设父子检查组合能力。

## 已确认的检查对象与边界

检查对象是指定目录中的 TypeScript 工程项目。标准描述的是我们对这类项目基础实践配置的要求，不只是 TypeScript 编译器选项。

- 检查项目是否正确配置了质量保障，不验证当前代码是否通过这些保障。
- lint、格式、测试、覆盖率要求、质量门禁及 CI 的配置均属于标准讨论范围。
- 项目对工具和版本的声明是项目事实；系统实际安装、全局命令、Node/npm 配对、nvm 管理及本机 registry 属于独立工具链 Check。
- 不执行项目脚本、动态 JS/TS 配置、类型检查、lint、测试、构建或 CI，不以现有报告、徽章或最近 CI 成绩替代配置证据。
- 允许等价配置、工具及目录布局；不强制项目继承 preset，也不强制文件名和脚本名与模板相同。
- 检测范围限制在目标项目目录，不自动向父项目或其他项目扩展。外部继承配置、符号链接及远程配置如何表达证据，需先定义支持边界，不能擅自越界读取或执行。

## 基础实践的配置目标

下表定义需要表达的目标，不代表第一期已经具备对应解析器。

| 领域       | 需要描述与验证的配置目标                                                   | 不属于合规结论的事实           |
| ---------- | -------------------------------------------------------------------------- | ------------------------------ |
| 依赖管理   | 声明包管理器及版本要求，保留对应 lockfile，配置可复现安装                  | 本机工具版本、实际安装是否成功 |
| TypeScript | 依赖声明、可解析的有效配置、严格性、源码与测试检查范围、模块及目标的一致性 | 当前类型检查是否无错误         |
| Lint       | 适用于 TS 的规则能力、需要时的类型感知、合理的目标范围与忽略规则           | 当前 lint 是否通过             |
| 格式       | 统一格式策略和不写文件的检查入口                                           | 当前文件是否已经格式化         |
| 测试       | 测试发现范围、非 watch 入口、无测试时的行为                                | 当前测试是否通过               |
| 覆盖率     | 启用采集、包含应统计的源码、指标和最低阈值、门槛执行入口                   | 当前覆盖率是否达标             |
| 质量门禁   | 聚合入口连接所要求的检查，子检查失败不被吞掉                               | 当前聚合命令退出码             |
| CI         | 要求的触发事件、冻结安装、质量门禁与覆盖率入口连接                         | 最近 CI 状态或运行结果         |

正确配置必须包含连接关系。例如，配置覆盖率阈值但 CI 从未调用启用覆盖率的入口，不能仅凭阈值字段存在判合规。忽略全部源码的 lint 配置同样不能凭工具配置文件存在判合规。

构建产物、npm 发布入口、exports、声明文件交付及消费者可用性不默认纳入本次基础契约；如需扩展，应单独明确目标及其与其他标准的关系。

## 输入分层

沿用 nodejs-toolchain 的 `context` 与 `requirements`
分层，但不沿用其宿主执行环境字段。

```json
{
  "context": {
    "projectDirectory": "D:\\Projects\\example"
  },
  "requirements": {
    "testing": {
      "coverage": {
        "minimum": {
          "branches": 80
        }
      }
    }
  }
}
```

- `context.projectDirectory`
  指定目标机的绝对项目目录，不接受命令、原始环境 map 或探测结论。
- `requirements`
  描述调用方要求，不让调用方提供“已经符合”的结果，也不退化为任意文件断言语言。
- 不提供 `executionEnvironment`，不隐含依赖 `check.nodejs-toolchain`。
- 整个 input 的结构校验与 requirements 的纯归一化是不同职责；normalize 不负责检查目录存在与读取项目。
- 调用方可省略 requirements 或仅描述差异；下文候选字段及数值仍需实施前确认。

## 默认与归一化：已确认语义

默认要求是标准的一部分，不能通过简单对象展开或通用深合并定义。内部必须有归一化函数，以任意未知值为输入，输出明确错误或完整一致的 requirements。

候选函数签名：

```ts
type NormalizeResult =
  | { ok: true; requirements: Requirements }
  | { ok: false; error: RequirementsError };

function normalizeRequirements(input: unknown): NormalizeResult;
```

`unknown`
是边界类型，不表示任意值都合法。签名及错误对象的具体字段是实施候选；已确认的要求是不能静默失败、不能以部分结果伪装成功。

### 默认与定制

- requirements 缺省或 `{}` 时，产生同一份默认工程基线。
- 仅提供局部要求时，由对应领域的语义补齐其他有效要求，不把父对象整体替换，也不机械合并未知结构。
- 默认基线应覆盖前述基础实践领域；具体阈值、工具选择及规则集合尚待确认。
- 数组候选语义为显式替换，不隐式追加；需要逐项确定合法值、重复值及空数组处理。
- 默认规则绑定准确的契约/制品版本，不随远端 preset、当前设备或时间漂移。
- 正常化后应能够解释本次实际生效的要求，不要求现在扩展公共 Check 输出协议。

### 启用、关闭与放宽

- 领域及有必要独立关闭的子能力应有明确启用状态；候选字段为 `enabled`。
- 明确关闭时，内部结果只保留关闭状态，不残留该领域的有效规则。
- 显式关闭又提供该领域要求属于冲突，应报错而非默默忽略。
- 能力要求为 `false` 表示不要求，不表示禁止被检项目启用该能力。
- 放宽某项要求与关闭整个领域必须可区分。
- 依赖关系依据有效要求判断，不能仅凭默认值残留制造冲突；若明确要求 CI 接入覆盖率而覆盖率领域被关闭，则报告冲突。

### 校验与错误

- 拒绝未知字段、错误类型、非法值及相互冲突的要求，不隐式将 `"90"` 转为数字。
- `null`、数组等不是合法的 requirements 对象；缺省输入是单独允许的默认请求。
- 覆盖率数值须为有限数字且在 `0..100` 内；是否只允许整数待确认。
- 错误应定位输入路径并说明原因，不能依赖原始异常文本或泄露其他输入。
- 输入非法不等于项目不合规，不能生成正常业务问题代替输入错误。
- normalize 应确定、无副作用、不修改调用方对象、不读取项目或设备，不运行命令。
- 完整的内部 requirements 不含需要检测器再次猜测的缺省值；后续检测逻辑只消费该结果。

### 代表性行为

| 输入情况                                 | 预期                           |
| ---------------------------------------- | ------------------------------ |
| requirements 缺省或 `{}`                 | 生成完整默认基线               |
| 只指定 branches 为 80                    | 按已确认政策补齐其他指标及领域 |
| 明确关闭 CI 且未提供 CI 规则             | 生成明确关闭状态               |
| 关闭 CI 同时指定 CI 规则                 | 返回输入冲突                   |
| 要求 CI 执行覆盖率但关闭覆盖率能力       | 返回跨领域冲突                 |
| 阈值 120、`"90"`、未知字段或错误嵌套类型 | 返回定位明确的输入错误         |

## 候选领域结构：尚未定稿

以下保留本轮讨论的表达方向，不将字段名或示例数值视为已批准 Schema。

| 部分                   | 候选要求                                                 |
| ---------------------- | -------------------------------------------------------- |
| `dependencyManagement` | 包管理器种类、声明版本下限、lockfile                     |
| `typescript`           | 依赖声明、有效严格性、附加安全选项、源码与测试覆盖范围   |
| `lint`                 | 类型感知、目标覆盖范围、要求的规则能力                   |
| `formatting`           | 只检查、不写文件的入口                                   |
| `testing`              | 非 watch 入口、无测试失败、覆盖率能力                    |
| `testing.coverage`     | 统计未触达源码；branches/functions/lines/statements 下限 |
| `qualityGate`          | 要接入的检查能力、失败传播                               |
| `ci`                   | PR/主分支 push 等触发、冻结安装、质量门禁接入            |

候选默认参考当前 preset 的 pnpm 声明、严格 TS、类型感知 lint 及四项 90% 覆盖率等实践，但用户尚未逐项批准。尤其不能直接把 NodeNext、ES2022、固定源码目录或 Node 类型当作所有 TypeScript 项目的默认目标。

## 实施前须确认

1. 各领域的具体默认值、可定制项与可关闭边界；明确 coverage 阈值和 TypeScript 附加安全选项。
2. 输入字段、合法取值、集合规则、错误结果和跨领域依赖的最终表示，避免将此文候选直接固化为协议。
3. `source`、`tests`
   等语义范围如何描述，不强制模板目录；是否需要可选的项目相对路径。
4. 后续实际检测支持的配置工具及动态/外部配置限制；本期只描述边界，不实现解析器。

## 后续实际检测的结果边界

应区分明确不满足、证据不足无法确认、输入非法及检查执行故障。未知配置形式不能猜测通过，故障不能变成普通 gap。具体问题码和现有 Check 契约的映射留待实际检测阶段设计，不在本期新增公共结果协议。
