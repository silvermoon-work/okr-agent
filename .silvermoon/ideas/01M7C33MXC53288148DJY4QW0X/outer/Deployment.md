# Deployment

## Steps

### D-S01: 固定本地验证候选

将最终部署契约同步到 primary 并固定其准确修订，再对相应本地候选、样例和适用构建产物验证；记录源码提交及本地产物摘要，不要求外部消费或发布。

候选为实现提交 `9c098ff3c76251ed314b581747a0103e4d75ec6b`，准确实现修订 `6b1a3b63a29c0181a379a0615e384a1bd593476c` 已由父代理在 primary `8676b55abe58eb48ecfe8b0ff4cf46b131cb54e0` 接受。保持已验收实现不变；核对生产 CAR 的 CID/SHA256，并将其与使用同一作者源码、仅注入既有确定性元数据 provider 的本地验证 CAR 分别记录，后者不能冒充生产 CAR。

### D-S02: 验证本地交付结果

在仓库内受控样例中验证准确候选的声明识别、npm/非 npm 分流及失败结果，保存可追溯证据。只运行检查器自身和获准本地验证，不执行被检查目标代码；不发 npm 包、不发版、不推送发布标签、不上传 IPFS/Pinboard、不部署或迁移 Cloudflare 资源。

复用已验收的 CAR/Engine 本地验证入口与固定资产，在操作自有的忽略目录构造普通 TypeScript、npm、Cloudflare、自定义类型及重复/逃逸/私有 npm/明确发布未登记等反例；目标源码、测试和 build 均为不可执行的受控输入。只执行检查器、内存 Engine、只读候选选择与计划生成，不执行目标脚本或实际 publisher。结果写入同层本地验证报告及原始 JSON；发现实现缺陷先报告，不在部署阶段修补。

## Acceptance criteria

### D-AC01: 修订可追溯

通过 primary 可达提交、部署契约准确修订及适用本地产物摘要证明本地验证使用同一候选，不以线上、registry 或远端 CID 可用作为门禁。

证据包含执行前已同步的契约修订、已接受源码/实现修订、生产及确定性验证 CAR 的独立身份、固定资产一致性和实际工具版本。实际 Node 与固定版本的差异继续显式披露，不改共享全局环境。

### D-AC02: 本地边界可验证

通过受控样例输入、通过/失败结果及可读诊断证明本地声明语义可用；明确仅为本地静态验证，不能声称外部消费、真实 npm 发布或 Cloudflare 运行/部署成功。

证明 npm 目标被精确选择、Cloudflare/自定义/未登记项不被 npm 调度，core 保持 private；正反例有预期结果，问题文档可读，Engine 任务被回收。生产制品仅核对身份，联网事实使用明确标记的确定性验证 provider；不以本地 mock 证明官方实时事实或线上权限。
