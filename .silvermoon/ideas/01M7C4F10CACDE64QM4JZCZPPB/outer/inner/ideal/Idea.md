# 按应用能力检查 Cloudflare 交付项

## 问题

通用 TypeScript 检查不能证明 Cloudflare 配置、前后端构建路由和 DO 等平台能力满足标准；直接复用旧检查也存在配置支持边界。

## 结果

以[第一阶段](../../../../01M7C33MXC53288148DJY4QW0X/outer/inner/ideal/Idea.md)已接受的交付描述和 TypeScript Check 为底座，在现有只读 Check 内为显式 Cloudflare 交付项增加按实际能力生效的有限平台检查。

## 边界

- 一个应用 Package 对应一个 Workers 部署目标，静态资产、服务端代码和多个 DO 类均为可选能力；不单列 realtime 类型。
- 复用根交付意图、既有单一输入/问题输出和适用通用质量门禁，不复制清单、不新建包或子 Task 协议。首期明确支持静态 Wrangler JSON/JSONC、资产、模块入口及本地 DO 的有限关系，边界见[首期范围](Scope.md)。
- 保持只读静态检查，不执行目标模块；部署只验证本地候选和样例，不要求外部消费。不发 npm 包、不发版、不上传 IPFS/Pinboard、不部署或迁移 Cloudflare 资源。

## 验收标准

- 静态前端、显式 API/SSR 模块入口和多个本地 DO 的样例均有按能力适用的配置检查；纯资产不强制 handler、资产 binding 或 Workers 测试插件。
- 平台配置、类型声明和测试配置与通用门禁一致；缺失、不匹配和无法确认明确区分，未知环境/构建/协议不能默认为通过。
- 本地标准、适用产物与文档引用准确可追溯，静态通过不被表述为外部消费、运行或线上部署成功。

本次只准备并提交构想；第一阶段部署结果与本构想均待父代理审查，不以提交代替接受，不开始实现。
