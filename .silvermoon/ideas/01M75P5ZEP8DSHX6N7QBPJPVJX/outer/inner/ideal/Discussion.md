# Preset 标准与 Check 组合讨论

本文是 [Idea.md](./Idea.md) 的 supporting
document。保留本轮讨论的方向、候选方案和未决事项，供后续深入讨论；不把建议写成已经获批的运行协议。

## 已形成的方向

### 标准、Preset 与 lineage 的职责

- 标准描述目标，Check 验证目标，Preset 提供满足目标的一种实现。
- Preset/git-lineage 适合快速创建以及后续模板更新；Check 适合根据当前事实发现问题、查缺补漏，不依赖项目是否继承过模板。
- Check 不替代代码更新合并，lineage 也不证明项目当前满足标准。
- Preset 自身应能接受相同 Check，避免模板与标准成为两份逐渐漂移的规则。
- 检查业务语义与交付能力，允许等价构建工具和布局；不将逐文件比对模板视为符合标准。

### 为什么不先做通用目录断言器

路径存在、类型、读写探测是可复用原语，但缺少项目目的，无法解释为什么需要该目录或如何合理整理代码。因此暂不迁移通用 directories
Check；待明确具体标准后再复用底层文件系统原语。同样，工具命令执行与版本比较不是完整的工具链标准，专用 Check 应拥有要求解释及修复参考文档。

### 首批候选标准

- `@silvermoon-work/check.npm-package`：重点考虑入口、类型、exports、交付文件、必要资源和消费者可用性。
- `@silvermoon-work/check.typescript`：先明确 TypeScript 项目的目标与能力，再决定规则，避免变成个人 tsconfig 开关偏好。
- 可继续讨论 pnpm monorepo 等标准，但不在本轮承诺完整迁移所有 presets。
- 本轮尚未盘点实际 preset 仓库及继承图；上面是候选方向，不是对现有 presets 内容的审计结论。
- Check 作者包采用 `check.<name>`
  命名；分发是否仅 CAR/CID 应另行明确，不默认增加 npm 发布。

## Requirements 的设计原则

调用方描述项目意图及允许的选择，而不是提供全部判定断言。例如下面仅是 npm 交付要求的示意，不是已定稿 Schema：

```json
{
  "requirements": {
    "runtime": "node",
    "delivery": {
      "moduleFormats": ["esm"],
      "types": true
    }
  }
}
```

规则、检测证据、具体问题码和修复文档由对应 Check 维护。哪些是标准必需项、哪些可配置、哪些属于另一个标准，需要逐项确认，不能为了适应任何项目而退化为任意政策语言。

## 标准依赖与子 Task

- 标准依赖通常是 DAG，不一定是单继承树。
- `context.invokeTask`
  是执行子检查的现有入口；父检查将自己的 requirements 显式投影成子检查输入，再检查本标准的附加要求。
- 模板继承可能只是为了复用文件，不必形成业务标准依赖。npm 包也不必然使用 TypeScript，是否依赖 TypeScript
  Check 取决于标准或明确要求。
- 子检查通过可继续；正常不通过使相应父级依赖要求不满足；执行故障和取消不转成普通 gap。
- 固定子 Bundle 的准确 CID，不能用 npm 包名或 `latest` 作为不可变执行身份。
- 重复/菱形依赖、输入不同的同一 Check、递归循环、预算与取消传播都需要明确规则；不能预先声称 Engine 已自动去重或防环。

## 结果与文档组合的问题

当前 Check SDK 通过 `reportProblem(code, brief)`
生成本 Check 声明的问题和相对参考路径，`invokeTask`
的作者入口返回子业务结果。父级不能直接把任意子 problems 拼进自己的 problems：

- 子问题码不一定属于父契约。
- 相对文档路径原本属于子输出根，拼接后可能错误地指向父输出。
- 用一个父级摘要问题代替全部子结论简单，但会损失诊断和修复细节。

候选方向是：业务结果保留层级，资源通过 IPFS 文件树组合。子问题码和文档维持原归属，不强行汇总为一个全局问题码枚举。

## IPFS 打包需要区分的两件事

### 子 Bundle 的分发

把依赖的执行制品与父制品一同交付，可以固定版本并改善离线分发，但把 CAR 当普通资源文件嵌入，不等于 Engine 会自动导入或授权执行。需要明确依赖声明、块闭包、根 CID、可获取性、导入/pin 及授权边界；CID 字符串本身不是 DAG 链接。

### 子运行输出的组合

将子输出根链接进父输出树，可能直接解决具体问题与参考文档的保留：

```text
父输出/
  references/          父级参考文档
  checks/
    typescript/        链接子检查输出根
    npm-package/       链接另一个子检查输出根
```

这个目录仅说明候选资源关系，不是定稿路径。若根中是实际 DAG 链接且块闭包可用，IPFS 可按内容寻址复用相同内容；不能因为路径名存在就声称完整可读。

结果仍需表示子检查身份、业务结果及相对文档的解析根。父级要获得子输出身份并具备链接能力；当前 CheckContext 尚不能直接完成这套作者流程。“打包子 Bundle”与“链接子输出”解决不同问题，不应绑定成一个不可拆分的设计。

## 下一轮待决问题

1. 从哪个实际 preset 开始抽取标准？哪些规则是必要交付目标，哪些只是模板选择？
2. npm-package、TypeScript、monorepo 等标准的独立边界与依赖条件是什么？
3. requirements 的最小模型及跨标准输入投影如何定义，是否需要显式配置适用性？
4. 父结果采用层级 children、依赖引用还是其他模型？整体 pass 与局部问题如何兼容现有 Check 契约？
5. 子调用如何公开准确输出 CID、来源与结果，输出链接能力应位于 Task
   SDK 还是 Check SDK？
6. 是否随父 Bundle 交付子 Bundle？离线导入与按 CID 获取各自需要哪些协议支持？
7. 子文档按哪个根解析？消费者如何递归浏览且不改写或错配相对链接？
8. 如何处理循环、菱形依赖、并发、重复执行、预算、授权、取消及资源回收？
9. 先做最小组合概念验证还是先实现独立 npm-package
   Check？哪些 API 变化需要上游配合？

## 后续验证方向

至少覆盖从 preset 派生与未派生但满足标准的项目、等价实现、真实不满足、多层子检查、故障/取消、输出文档读取和独立 CAR 消费。具体标准尚未确认，因此本轮不写预定测试结果、不生成新制品、不承诺自动修复或外部发布。
