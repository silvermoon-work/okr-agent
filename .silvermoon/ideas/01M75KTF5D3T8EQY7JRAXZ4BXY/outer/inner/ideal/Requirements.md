# Node.js 工具链检查要求

本文是 [Idea.md](./Idea.md) 的理想世界 supporting
document，定义业务要求、边界及可观察场景；不规定内部模块或检测命令实现。

## R-01: 产品与交付边界

- npm 包名为 `@silvermoon-work/check.nodejs-toolchain`，展示名称为 Node.js
  Toolchain Check。
- 本组织的 Check Task 包采用
  `@silvermoon-work/check.<name>`；基础设施 SDK/Builder 不因此重命名。
- 保持现有一个 npm 包、一个 Check 项目、一个标准 Task
  Bundle 的作者模型，不为本需求增加多 Check 模板。
- 使用当前 Check Task
  SDK/Builder 的 TypeBox 契约、问题报告与输出参考文档协议，不复制旧运行时或构建生成链。
- 可复用 potential-guide 的版本比较、进程控制与回归测试经验，但不迁入通用 tools 公开契约、旧 Host 或 Objective 调度。

## R-02: 输入结构

输入由执行上下文与复合 requirements 组成，描述调用方的要求，而非命令列表或探测结果。

```json
{
  "context": {
    "projectDirectory": "D:\\Code\\demo"
  },
  "requirements": {
    "tools": {
      "node": { "minimumVersion": "22.13.0" },
      "npm": { "minimumVersion": "10.0.0" },
      "pnpm": { "minimumVersion": "11.22.0" },
      "nrm": {}
    },
    "pairing": {
      "npmWithNode": true
    },
    "management": {
      "provider": "nvm",
      "appliesTo": ["node", "npm"]
    },
    "registries": {
      "active": {
        "npm": {
          "allowedUrls": ["https://mirrors.cloud.tencent.com/npm/"]
        },
        "pnpm": {
          "allowedUrls": ["https://mirrors.cloud.tencent.com/npm/"]
        }
      },
      "nrm": {
        "required": [
          {
            "name": "tencent",
            "url": "https://mirrors.cloud.tencent.com/npm/"
          }
        ]
      }
    }
  }
}
```

示例版本、目录和 registry 仅为调用方输入示例，不是包的默认政策或全平台最低版本。其他消费者可以声明不同 URL 或多个允许的 URL。

字段名和精确 Schema 在实施时定稿，但不得改变本文约束语义或静默扩大检查范围；如需改变业务要求，应先修订本理想世界。

## R-03: 执行上下文

- `context.projectDirectory`
  为执行机器上的绝对、已存在项目目录，显式提供，不依赖 Worker 偶然的 cwd。
- 检查 Task 实际执行环境，不检查提交请求的控制机，也不扫描机器上所有安装后挑一个合格版本。
- 工具检查、配对检查与 registry 检查使用同一个明确上下文，定位当前实际生效的可执行入口和配置；路径发现不等于验证可用。
- 区分项目本地配置、用户配置、环境变量等对有效 registry 的覆盖；不能只读取 nrm 列表或单个配置文件推断最终状态。
- 检测只处理必要的非秘密事实，不输出完整环境变量、完整用户配置或认证信息；输入 URL 禁止内嵌凭据。
- 不执行项目 lifecycle scripts 或任意项目代码来证明工具链状态。

## R-04: 工具自身要求

- 支持明确枚举的
  `node`、`npm`、`pnpm`、`nvm`、`nrm`，不接受任意工具名、自定义 command、shell 或安装脚本。
- 声明一个工具就要求它存在且可用；`{}` 不限制版本；`minimumVersion`
  要求当前版本不低于指定版本。
- 版本下限采用非负整数点分形式，第一版不接受 npm
  SemVer 范围；比较按数字段且不依赖浮点精度。
- Node/npm 通常配套但不能据此推断 npm 存在；pnpm、nvm、nrm 均非全环境必备，不默认要求安装。
- 未声明且未被其他约束依赖的工具不要求、不产生缺失问题；允许存在额外工具。
- 显式声明但不支持检测该工具的平台，不能跳过后宣称通过。

## R-05: Node/npm 配对

- `pairing.npmWithNode: true`
  要求当前 npm 属于当前 Node 对应的安装环境，而不只是二者版本各自合格。
- 此要求不依赖 nvm，可用于系统安装或其他管理方式。
- 启用时必须显式声明 `tools.node` 和 `tools.npm`。
- Node 与 npm 各自合格但来自不同安装环境时，报告配对不符；无法建立关系时不得声称配对通过。
- 不因本约束隐式要求 npm 是该 Node 最初随附的精确版本，也不扩展为 Node/npm 全版本兼容性矩阵。
- 省略本约束不要求配对；显式 false 若允许，只表示不检查，而非要求二者不配对。

## R-06: 当前由 nvm 管理

- `management` 可省略；省略代表不限管理方式，不增加 `any` provider。
- 第一版 `provider` 仅接受 `nvm`，不预先承诺 fnm、Volta 或任意 provider。
- `appliesTo` 为非空、无重复列表，第一版只允许 `node`、`npm`，且引用项必须在
  `tools` 中声明。
- 管理约束隐含要求 nvm 可用，无须额外重复声明
  `tools.nvm`；显式声明时还需满足相应版本要求。
- 验证当前生效工具受 nvm 管理，而不是仅发现 nvm 安装目录、环境变量或可执行文件。
- npm 要验证其自身与受管环境的关系，不能只由 Node 受管推断 npm 受管。
- 不声称证明历史安装过程，也不因为两个工具都受 nvm 管理而自动推断它们属于同一版本环境；配对由 R-05 明确约束。
- Unix nvm 与 nvm-windows 是不同实现，需独立适配和验收；Unix
  shell 函数不能当普通可执行文件处理。
- 未支持的 provider 或工具管理关系属于非法输入，不静默降级；证据不足不得返回通过。

## R-07: registry 只检查两类状态

### 当前有效 registry

- `registries.active.npm.allowedUrls` 与 `registries.active.pnpm.allowedUrls`
  分别声明允许的默认 registry，列表非空。
- 当前有效 URL 匹配任意一个候选即满足，npm 与 pnpm 分别核验，不能相互推断。
- 目标包管理器必须在 `tools`
  中声明；省略某包管理器的 active 要求则不限制其 registry。
- 各包管理器的项目上下文、配置覆盖优先级和有效配置必须与 R-03 一致。
- 多候选不表示自动选择、切换、故障转移或逐个网络探测。

### nrm 注册要求

- `registries.nrm.required` 为非空列表，每项指定非空 `name` 与对应 `url`。
- 所有要求项都必须存在且 URL 匹配，允许 nrm 中存在额外注册项。
- 此要求隐含 nrm 可用，无须重复声明
  `tools.nrm`；同名冲突 URL 属于非法输入，不尝试同时满足。
- nrm 注册正确不证明 npm/pnpm 当前使用它，当前使用正确也不证明 nrm 已注册。

### URL 与范围边界

- 只接受无内嵌凭据的 HTTP(S) registry URL；比较规则明确且有测试，允许尾部 `/`
  的等价形式。
- 不把 HTTP 与 HTTPS、不同主机、不同端口或有意义的路径当成同一 registry；不以不受控字符串前缀判断匹配。
- 第一版不检查 scoped
  registry、认证、下载/发布权限或网络可达性，不根据配置匹配声称可以安装或发布。
- 不将示例中的本机 registry 偏好硬编码为其他设备、CI 或消费者的要求。

## R-08: 输入一致性

- 至少有一项实际要求；拒绝空 requirements、空约束对象、空候选列表、未知字段和未知枚举。
- 拒绝引用未声明工具、无效版本、非法路径/URL，以及同一工具只能使用一个当前默认 registry 时互相排斥的要求。
- 对空列表、重复项及等价 URL 的规范化有确定规则；不静默丢弃非法要求。
- 不能用默认安装全套工具、自动猜 provider、执行失败后跳过等方式制造通过。
- 是否增加检测预算属于实施层执行控制，不混入工具链业务要求，也不覆盖 Engine 的 Task 生命周期语义。

## R-09: 结果、问题与参考文档

- 使用现有 SDK 的 `pass`、`problems[{code, brief, documentation}]`
  与输出相对文档路径，不增加旧 `target/actual` 结果字段或在业务结果内嵌 CID。
- 只有实际不满足项进入问题列表；通过结果没有 problems，不通过必须至少有一个具体问题。
- 工具缺失、不可用、版本不足/无法解析、配对不符、管理关系不符、当前 registry 不符、nrm 注册缺失/URL 不符具有能定位的具体问题分类。
- 每个公开问题码有对应参考文档，默认提供简体中文，包含适用范围、含义、安装或修复选择及复验方法；不只提供“重新安装工具”的万能文档。
- 修复指引尊重调用方要求：例如要求 nvm 管理时不能建议改用不受管安装；不限定管理方式时不能强迫安装 nvm。
- brief 说明相关工具、要求与实测事实；遵守 R-03 的秘密与输出边界。
- 无法建立配对或管理证据时必须明确表达不可确认；不得误报为“明确不受管理”。未知实现或检测机制失效应作为执行故障，不作为正常工具不满足。
- 超时、取消、意外检测故障及进程/资源清理失败保持执行故障，不伪装成业务问题或通过。
- 整体故障不被此前已经收集的问题覆盖；故障不得产生成功形状的替代结果。

## R-10: 无修改与支持范围

- 不安装或升级工具，不运行 nvm use、nrm
  use，不修改 PATH、npm/pnpm 配置、项目文件或 shell profile。
- 必要的专用临时资源由检查清理，子进程受限并支持取消；不得影响共享机器上的其他任务。
- 不自动修复、检查依赖完整性、运行实际构建、验证网络健康或证明整个应用 stack 可用。
- Windows 与 Unix
  nvm 的平台差异必须显式列入支持矩阵；发布只声称已验证的组合。无法支持的平台应明确失败，而不是回退到另一个环境。
- 声明工具的版本命令成功不代表任何命令都可信；执行环境与输入来自获授权调用方，Worker 不是安全沙箱。

## R-11: 最小可观察验收场景

| 场景                                      | 必须观察到的结果                                          |
| ----------------------------------------- | --------------------------------------------------------- |
| 仅声明 Node，其他工具缺失                 | Node 合格即可通过，不补充隐式全套要求                     |
| 分别声明版本下限                          | 相等/更高通过，更低准确定位；数字段比较不溢出             |
| 指定工具缺失、不可用、版本输出无法解析    | 明确对应问题，不混淆安装状态与解析状态                    |
| Node/npm 版本合格但来自不同安装环境       | 启用 pairing 时不通过，未启用不因配对而失败               |
| 安装了 nvm，但当前 Node 或 npm 不受其管理 | 对应管理要求不通过                                        |
| Node 受管但 npm 指向其他位置              | 不以 Node 的管理结论代替 npm 的结论                       |
| 省略 management，工具由其他方式管理       | 不因未使用 nvm 而失败                                     |
| 未知 provider、无效引用、空要求或冲突配置 | 输入被明确拒绝，不转成正常业务结果                        |
| npm/pnpm 当前 registry 分别命中允许列表   | 各自通过；多候选只需命中一个                              |
| 项目或环境变量覆盖用户 registry 配置      | 结论对应实际项目有效值，而非 nrm 显示值                   |
| nrm 指定名称缺失或同名 URL 不符           | 分别报告；额外注册项不影响通过                            |
| URL 仅尾部斜线不同；协议或路径不同        | 前者按等价规则比较，后者不能误判相同                      |
| 检测超时、取消或清理失败                  | Run 故障/取消，无伪造 Check 结果与遗留子进程              |
| 正常通过和多项不满足                      | 真实 Engine 验证结果形状，并通过输出 CID 读取对应参考文档 |
| 检查前后比较环境                          | 工具选择、registry、项目及用户配置未被修改                |

实施时结合受控 fixture 与真实工具环境验证；不得以测试替身通过推断真实 nvm 或包管理器配置行为已经验证。
