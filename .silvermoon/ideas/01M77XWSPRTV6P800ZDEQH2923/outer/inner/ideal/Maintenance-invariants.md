# 长期最佳实践与动态维护事实

本文补充 [Idea.md](./Idea.md)、[TypeScript 标准](./Requirements.md) 与
[npm 包项目标准](./Npm-package-standard.md)。本轮只修订设计文档，不声称当前实现已支持联网维护检查，也不改写已完成 idea 的历史验收。

## M-01: Check 的定位

Project
Check 描述我们认为怎样配置和持续维护同类项目是好的，是开始后续迭代、维护前的检查依据，而不是保证从此永远通过的静态证书。

- 固定的是长期规则，不是模板文件、作者机器版本或发版时的版本快照。
- Check
  CID 固定规则与实现，项目目录定位对象；外部事实在观察时获取。因此同一项目、同一 CID 随上游发版从通过变为不通过是合理结果。
- 规则本身变化需要新 CID；版本事实变化不要求修改 Check 代码或重新发布制品。
- 不要求不断后台轮询，不在本次引入定时任务或自动修复；每次执行判断当轮可证实的状态。

## M-02: pnpm 同 major 保持最新稳定

1. packageManager 必须声明精确 pnpm 稳定 SemVer，可保留现有支持的完整性后缀；不能使用 latest、范围或 prerelease 来替代可复现锁定。
2. 以项目锁定版本的 major 为边界，从可信发布元数据选取该 major 中最高的稳定 minor.patch，与项目锁定版本比较。
3. 落后于同 major 最新稳定 minor 或 patch，正常不通过并指导维护者更新声明、lockfile、CI 选择后复验；不由 Check 自动安装、改配置或更新文件。
4. 只发布更高 major 不触发跨 major 升级要求。排除 prerelease，不把全局 latest
   dist-tag 当成某个历史 major 的最新版本。
5. 不再以 pnpm >=11.22.0 之类历史常量代替维护要求；具体旧 major 是否已停止支持，是另一条需要可靠生命周期依据的政策，不从版本号大小或新 major 存在推断。
6. 同 major 最新版本若不能运行在项目所选执行环境中，应报告已知兼容冲突或无法确认，不悄悄把“最新”改成“能运行的最高旧版”。保持最新不证明它一定满足所有 registry 新要求，也不代替实际兼容性验证。
7. CI 应使用项目精确锁定的包管理器并执行 frozen
   lockfile；新鲜度和可复现性是互补要求，而非二选一。

## M-03: 规则、外部事实与项目事实分层

- 规则：如“所选 pnpm major 内最新稳定版本”，属于 Check 身份。
- 外部事实：发布版本集合、来源、新鲜度和观测时间，属于本次证据。
- 项目事实：packageManager、CI 的实际配置及范围，来自只读项目观察。
- 结果至少能够通过报告摘要及输出证据定位锁定版本、major、观察到的最新稳定版本、元数据来源与时间；不能只给一个无法解释的“过时”。
- 不强制把证据塞进当前 pass/problems 业务结构；可作为输出资源交付，但不得泄漏认证值、完整环境、源码或本地敏感配置。

## M-04: 元数据查询与新鲜度边界

- 输入仍只有 projectDirectory，不增加 registry
  URL、最新版本、时钟、skipFreshness 或离线豁免等业务参数。不能把项目自报的“最新”当外部证据。
- 网络只读取公开或已获授权的发行元数据，使用标准明示的来源政策与宿主批准的访问配置；不执行目标 npm/pnpm 命令，不下载执行包，不根据不可信项目 URL 任意外连。
- 不硬编码本开发机的镜像政策为其他设备、CI 或消费者要求；宿主源选择不能静默改变“最新稳定”的语义。镜像存在已知缺项、延迟或冲突而无法证明完整性时，不能直接据此判通过。
- 缓存必须有明确有限的新鲜度窗口，记录来源与实际观测时间；具体来源、窗口和查询预算应在实施前写入实施契约并验证，不能依赖无限缓存、假时间或请求失败后回退陈旧快照。
- 需要完整的同 major 候选元数据；未知响应、不可验证时间、网络/认证失败、超时、过期缓存、来源冲突或无该 major 候选时明确表达无法确认。不得制造默认版本、误报为确定落后或返回 pass:true。
- 采用故障或非通过的 unconfirmed 分类时须保持 SDK/Engine 既有错误职责，并在实施契约明确；无论如何不得静默成功。取消仍是取消，意外检测故障仍是故障。
- 父子组合保留观测来源及时间；同轮复用事实时必须明确来源和有限生命周期，不把几轮不同时间的事实假装成同一快照。

## M-05: Node.js 工具链的后续调整原则

Node.js
toolchain 后续也应使用长期政策表达默认最佳实践，而不是不断更换最低版本常量：

- 默认实际生效的 Node 应属于官方仍支持的 LTS 系列，不能仅凭偶数 major 或版本足够大就通过；已 EOL、尚未进入 LTS 的 Current 与 prerelease 不满足该默认政策。
- “仍受支持的 LTS”不等于“最新 LTS”：前者允许仍在维护的旧 LTS，后者会迫使跨 major 迁移。本轮采用前者作为方向，不暗中要求自动切 major。
- 精确运行版本仍可锁定以保证可复现；查询官方发行/支持周期事实验证 LTS 状态，而不是把 LTS 别名当成已生效版本证据。
- nvm 管理、Node/npm 配对、registry 选择与版本新鲜度是不同关系，不能互相推断。
- 这是现有 nodejs-toolchain 后续修订的设计依据，不自动纳入本次两个 Project
  Check 的实现任务，不取消其执行环境授权边界，也不重写已交付 CAR 或完成状态。
- npm 库允许哪些消费者 Node 版本与开发机默认使用哪个 Node 系列不同，不能因为开发应使用 LTS 就一律禁止库支持其他兼容版本。

## M-06: 验证原则

- 受控发行事实覆盖：同 major 新 patch、新 minor、更高 major、prerelease、已锁定最新、缺少候选、数据过期、镜像冲突、网络故障与取消。
- 同一 Check 与项目 fixture 在两组受控发布事实下可从通过变为不通过，证明固定的是规则而非版本常量；受控数据不能冒充真实“当前最新”。
- 真实 Engine/CAR 消费另验证获授权元数据查询、证据读取与完整错误传播，不依赖作者源码或宿主直接检查代替。
- Node 后续实现需覆盖受支持 LTS、已 EOL
  LTS、Current 与 prerelease 的真实生命周期语义；本次文档不宣称这些场景已实现或通过。
