# 人机协作与三套 Spec

## 问题与用户期望

作为 Silvermoon 使用者，我希望通过逐轮表达、具象示例和有重点的审核，把模糊想法形成可执行共识，从而不必一次讲完全部需求，也不必在实现、部署完成后重复 Agent 的检查。

旧的 Implementation / Deployment 结果型 sign off 不再是新模型的人工关口。人确认的是做什么、采用什么关键方案和怎样才算完成；Agent 负责理解、编辑、调研、执行和举证。

以下是本轮讨论的需求约定，不是已经完成的新产品实现。CLI 的具体命令、交互文案和机器协议尚待设计，不在此虚构最终用法。

## 第一阶段：需求澄清，产出 Requirement Spec

核心问题：

1. 用户背后要解决的问题、真正诉求是什么？
2. 用户希望感知到什么变化？

协作循环是“人表达 → Agent 理解并 illustrate → 人判断、补充或纠正 → Agent 更新文档”，直到人明确 sign off。

表达采用“描述 + 案例”，而非只有抽象目标：

- UI 变化使用 Mock UI；
- CLI 变化使用具体命令、参数、输出及必要的错误交互示例；
- API 变化使用请求、响应及相关行为 Example。

User Story 可表达为“作为某角色，我希望获得某能力或变化，从而解决某问题或获得某价值”。UX、CLI 和 API 的可见细节属于产品需求，可以在本阶段明确；排除的是把内部实现方式误当成用户诉求。

用户提出的实现方案可保留为候选，不自动升级为必要约束；确实不可替代的约束需明确确认。

Agent 的 propose 已表达其理解，不额外引入一套对称的 Agent sign off。人的 sign off 表示“这准确表达我的意思”，不等于批准任意后续发布或生产操作。

## 第二阶段：技术调研与设计，产出 Technical Spec

Agent 主动基于 Requirement Spec 和项目现状开展工作，无需等待人先提供技术问题。

### 第一轮同步：调研问题

Agent 先做足以形成问题列表的项目探索，提出需要调研的问题。人从中标记自己关心的项目，或补充问题。

Agent 的责任范围应覆盖人的关注项，也包括实现者必须考虑的其他问题；人没有选中的问题不因此被删除或免除调研。

### 第二轮同步：结论与推荐方案

形成两类相互关联的文档：

1. 人需要 review 的关键问题与决策文档：结论、候选方案、取舍、推荐方案及影响；
2. Agent 仍需关心的补充技术文档：其他调查、业务模型、架构设计、依赖与风险等。

两者共同构成 Technical Spec，不能只有问题列表或调研流水账。面向人的关键结论应得到人的 review / sign off；不能以“属于补充文档”为由隐藏影响需求、重大风险或用户取舍的决策。

发现与需求冲突、不可行假设或需要产品取舍时，Agent 提问并回到相应需求内容修订，而不是在技术方案里默默改变需求。技术设计应足以指导实现，不要求提前穷举每个类、函数或实现任务。

## 第三阶段：验收约定，产出 Test Spec

### 第一轮同步：场景目录

按逻辑分类列出需要测试的场景、环境及 Implementation / Deployment 归属，与人对齐覆盖范围。

### 第二轮同步：文字版用例

Agent 细化用例的前置条件、操作、预期结果和证据要求，由人 sign off。这里产出文档，不在需求讨论时提前编写自动化测试代码。

- Implementation：实现阶段将相应用例落实为 UT、Integration Test 等自动化测试，一般无需人继续参与执行。
- Deployment：Agent 到适当环境，按文字用例操作验证；“手工测试”表示按步骤执行，不表示交给人测试。

上述是本轮确定的主要分工。混合测试、真实平台探测等边界应在具体 Test Spec 中明确，不能仅按“是否自动化”偷换被验收的对象或环境。

Test Spec 验证需求和必要的技术约束，不仅证明“代码照 Technical Spec 写了”。需要判断的结果同样要规定依据，不能将“Agent 认为完成”作为充分证据。

## 修订与重新达成共识

三个阶段是逐步形成共识的协作节奏，不是不可回退的流水线。

Agent 发现约定不可行、不适用或不完整时，可以直接编辑相应文档提出修订，保持未提交，让人通过工具查看相对已批准内容的 diff，再作 sign off。

- 草稿不自动替代现有共识；不能按未批准的新标准宣布完成。
- 修改目标、边界、关键方案或验收要求后，重新确认受影响的约定；具体依赖与失效判定留待技术设计。
- 已有确认、版本和验收证据保留可追溯性；只对仍适用的证据复用，受影响的结论重新验证。
- 阻碍当前工作的疑问应明确提出，不等待人反复追问“是否 ready”。执行失败应先尝试解决，不得通过降低标准自行通过。
- 未决事项、业务不通过、执行故障和证据不足不能混为成功。

取消执行结果的人工验收不取消操作授权。npm 发布、生产变更、费用及破坏性动作仍受独立授权约束。
