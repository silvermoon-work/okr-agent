# Deployment

本契约使用旧 Silvermoon 部署门限。`@silvermoon-work/silvermoon@0.1.0-rc.0` 已发布但未通过真实闭环，发布事实与缺口保留在[部署记录](deployment-readiness.md)。用户要求按[Inner 修复决议](inner/rc0-resolution.md)重新实施，并在完成后发布新的连续 RC，再回来验证；新候选为 `0.1.0-rc.1`、准确源码提交 `938751db3cc15fabccf156ad60825f02e842eccb`，对应 [main-push CI](https://github.com/silvermoon-work/okr-agent/actions/runs/44219803173)。主 Agent 受托负责生命周期验收；发布仍须绑定准确版本、提交及全部前提，不能复用 `rc.0` 成绩证明新版本完成。

## Steps

### D-S01: 验证发布前提并交付授权版本

核实准确提交的 CI、依赖和发布条件，取得明确发布授权后交付指定版本；旧 alias 转发单独确认。

### D-S02: 在独立环境试用新 Silvermoon

仅在新包发布后，以独立受控环境安装准确版本，按约定用例完成共识、实现与部署验收流程，避免污染当前旧流程。

### D-S03: 保存真实证据并确认过渡边界

归档版本、环境、操作结果及异常恢复证据，验证旧数据保留和显式切换边界；本 Idea 的最后验收仍使用旧 Silvermoon。

## Acceptance criteria

### D-AC01: 授权交付可核验

以发布记录、准确版本/提交及独立安装结果证明目标包可取得、可运行；若授权 alias 切换，另以真实安装验证转发行为。

### D-AC02: 新协作闭环可实际运行

以独立环境的操作记录证明三套 Spec 的人机确认、修订、整备阻断以及 Agent 实现/部署验收可通过真实 CLI 推进，不以单元测试替代外部结果。

### D-AC03: 旧流程不被隐式改变

记录试用前后旧 CLI、项目历史及旧 Idea 的状态，证明未被新安装或试用自动迁移、覆盖；任何正式切换有明确选择与可追溯记录。
