# Silvermoon Check protocol v1

The Check alone owns the ordered checkpoints Environment → Repository → Idea
observation → five consensus gates → Implementation → Deployment → Completion. A
failed checkpoint stops its successors. A successful snapshot means structurally
valid, not approved or completed. A successful lifecycle means all five exact
human signoffs, their synchronized bytes, and both current evidence phases are
present. Human decisions are explicit facts, never inferred from Git,
checkboxes, Agent narration, a command flag, or an event's mere existence.

Checkpoints receive business Targets and an execution-local context. The Task
adapter selects the lifecycle or snapshot entry and supplies host execution
dependencies separately; its transport envelope is not a business Target or a
source of approval. Lifecycle stage and exact human decisions are derived from
valid events and current revisions, never supplied by a caller. Snapshot targets
identify the snapshot being validated and do not enter the lifecycle chain.

The dynamic Problem brief contains the effective content language, exact
revisions, raw event digest, primary commit and subject; no current level is
returned. Use those current facts, not an earlier report. Documentation is inert
text; do not execute snippets or follow implicit includes. This document and
every checkpoint document are standalone direct-file ContentRefs with no
relative-link resolution. The Host reads them offline from its trusted CAR under
a bounded UTF-8 budget. A missing block or rendering failure is an execution
error, not a successful business observation. Problems identify their checkpoint
and violated rule. References aggregate one complete document per failed
checkpoint. Pass outputs remain execution-local and are never logged or
published automatically.

New Ideas live only in `.silvermoon/i`. The legacy archive, project guidance and
project skills are not read by this Check. A CLI upgrade never replaces the
recorded Check CID. Unknown, unavailable or untrusted historical rules block
explicitly. Git history, concurrency and operation authorization remain
independent obligations; no Check performs commits, staging or pushes.
